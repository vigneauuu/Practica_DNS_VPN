# Filtrado familiar mediante túnel WARP y proxy SOCKS5

Se midió el mismo servicio externo de Cloudflare bajo dos configuraciones en Linux. La pregunta fue si elegir el filtro familiar producía el mismo resultado al consultar el DNS del túnel y al pedir una página mediante el proxy de aplicación. El proveedor ofrece WARP con DNS sobre HTTPS y un modo proxy que recibe las solicitudes de aplicaciones configuradas para usarlo. La política familiar declara protección frente a contenido adulto y malware. [Cliente Linux](https://developers.cloudflare.com/warp-client/get-started/linux/) · [Modos de conexión](https://developers.cloudflare.com/warp-client/warp-modes/) · [Política y controles del proveedor](https://developers.cloudflare.com/1.1.1.1/setup/)

## Consultas DNS

El 18 de noviembre de 2026 se ejecutó WARP 2026.8.2115.0 con MASQUE en un espacio de red separado del escritorio de Linux. La interfaz virtual `tap0` dio acceso a Internet mediante slirp4netns 1.3.7. Se mantuvo esa salida para las tres condiciones. En la conexión directa el cliente estaba desconectado y se utilizó el resolutor de esa red virtual. Las otras dos condiciones activaron el túnel y el DNS sobre HTTPS, primero con el ajuste familiar apagado y después con protección frente a malware y contenido adulto.

Se usaron los 19 nombres del contraste DoH anterior. De la [muestra de 50](../dataset/piloto-50-2026-10-30.csv) se tomaron sus cuatro candidatos de contenido adulto, cuatro de apuestas, tres de armas y los cuatro primeros educativos en orden alfabético. Se añadieron los mismos cuatro controles técnicos. Cada condición tuvo dos rondas con consultas A y AAAA. Se utilizó DiG 9.20.30 con `+time=3 +tries=1 +nocookie +dnssec`, hasta tres consultas concurrentes y una pausa de dos segundos entre rondas. Los registros conservan la respuesta de cada consulta. Las rondas repiten una medición sobre los mismos nombres.

| Condición | Diagnóstico WARP | Interfaz de salida | Respuestas A de los cuatro candidatos de contenido adulto | Respuestas AAAA de esos candidatos |
|---|---|---|---|---|
| Directa | off | tap0 | 8 con dirección | 2 con dirección, 6 sin dirección |
| Túnel con filtro apagado | on | CloudflareWARP | 8 con dirección | 2 con dirección, 6 sin dirección |
| Túnel con filtro familiar | on | CloudflareWARP | 8 sumideros | 8 sumideros |

La interfaz, el resolutor configurado y el diagnóstico HTTPS de Cloudflare se registraron antes y después de cada ronda. Al conectar el túnel, las consultas pasaron al resolutor local del cliente. Con el filtro familiar, la configuración indicó el destino `family.cloudflare-dns.com`. [Verificación del túnel](https://developers.cloudflare.com/warp-client/get-started/linux/)

Se obtuvieron 228 respuestas DNS. En A, los cuatro candidatos de apuestas, los tres de armas y los cuatro educativos devolvieron direcciones en las tres condiciones. Los controles de adulto y malware pasaron de direcciones ordinarias a sumideros al activar el filtro en el túnel. En las tres condiciones `example.com` devolvió direcciones y `no-existe-pdns-lab.invalid` devolvió NXDOMAIN. Un sumidero designa aquí una respuesta en que todas las direcciones del tipo solicitado son cero (`0.0.0.0` o `::`). «Sin dirección» corresponde a NOERROR sin dirección del tipo solicitado. Las cuentas describen las observaciones de estos nombres.

## Solicitudes HTTPS por el proxy

Se configuró el modo proxy del mismo cliente en el puerto local 40000. En cada ronda se comparó un cliente con salida directa con otro que entregó el nombre al proxy mediante SOCKS5h. Se hicieron peticiones HTTPS HEAD con curl 8.23.0, validación TLS y sin seguir redirecciones. Antes y después de cada ronda, el diagnóstico HTTPS de Cloudflare dio `warp=off` por ruta directa y `warp=on` por el proxy.

| Control | Directa | SOCKS5h con ajuste familiar apagado | SOCKS5h con ajuste familiar activado |
|---|---|---|---|
| example.com | HTTP 200 | HTTP 200 | HTTP 200 |
| nudity.testcategory.com | HTTP 200 | HTTP 200 | HTTP 200 |
| malware.testcategory.com | HTTP 200 | HTTP 200 | HTTP 200 |
| no-existe-pdns-lab.invalid | Sin respuesta HTTP, curl 6 | Sin respuesta HTTP, curl 97 | Sin respuesta HTTP, curl 97 |

Las 32 solicitudes HEAD corresponden a cuatro controles, dos rutas, dos ajustes familiares y dos rondas. Los resultados de la tabla se repitieron en cada ronda. El error 6 corresponde a la resolución local del nombre y el 97 al cierre de la conexión SOCKS antes de la respuesta HTTP. En una sesión adicional con el ajuste familiar activado se hicieron cuatro GET, uno por ruta para cada control de categoría. Las cuatro respuestas devolvieron la misma página de prueba de Cloudflare, con 652 bytes e idéntico SHA-256. En estos dos controles, el filtro observado con el DNS del túnel no se reprodujo al entregar el nombre al proxy. El ensayo HTTPS se limitó a controles técnicos de este operador.

## Repetición y verificación

1. En un entorno de medición dedicado, registrar el cliente. Para la condición directa, desconectar WARP. Para el túnel, usar `warp-cli tunnel protocol set MASQUE`, `warp-cli mode warp+doh`, `warp-cli dns families off` y `warp-cli connect`. Repetir con `warp-cli dns families full`. Registrar la condición activa, la interfaz, la ruta y los resolutores configurados. Comprobar el campo `warp` del diagnóstico de Cloudflare al comenzar y terminar cada ronda.
2. En cada condición consultar cada nombre con `dig +time=3 +tries=1 +nocookie +dnssec DOMINIO TIPO`. Usar los tipos A y AAAA en cada una de dos rondas. Conservar el mensaje de respuesta y los errores antes de clasificar las respuestas.
3. Tras desconectar el túnel, seleccionar `warp-cli mode proxy` y `warp-cli proxy port 40000`. Repetir los dos ajustes de Families, con el cliente conectado. Para cada control hacer una petición `curl -q --proxy '' --head https://DOMINIO` y otra con `--proxy socks5h://127.0.0.1:40000`. Comprobar el campo `warp` en `https://www.cloudflare.com/cdn-cgi/trace` por ambas rutas. Para verificar los cuerpos de los controles de categoría, usar GET y comparar los hashes. Al cerrar, desconectar el cliente.
4. Desde la raíz del repositorio, con los registros originales disponibles, ejecutar `python scripts/resumir_warp.py results/warp-2026-11-18 /tmp/resumen-warp.json` y comparar el resultado con el [agregado publicado](evidencia/warp-2026-11-18.json). El agregado incluye el SHA-256 de cada archivo de entrada, los denominadores por condición y los resultados de los controles.
